# Market Note updates

- New daily reports are content-driven. Create exactly one completed JSON file at `content/daily/daily-YYYY-MM-DD.json`. Do not add new daily reports to `app/page.tsx`.
- The JSON filename and `slug` must match. Required top-level fields are `slug`, `kind` (`日次レポート`), `date`, `dateTime`, `title`, `headline`, `excerpt`, `description`, `label`, `displayDate`, non-empty `sections`, and a non-empty `disclaimer`. Use the latest JSON file as the structural template.
- `lib/article-content.ts` discovers `content/daily/daily-*.json` automatically. `app/page.tsx` merges this content with the legacy registry, and `app/articles/[slug]/page.tsx` generates the individual daily page. A completed daily JSON file therefore supplies the article page, latest section, and archive without a second manual registration step.
- `legacyArticles` in `app/page.tsx` exists only for older static routes and non-content-driven reports. Preserve those entries. Do not move a new daily report into `legacyArticles`.
- Keep the shared header immediately followed by `main.site-shell` and its first section, `section.market-hero`. The user explicitly removed reports above the photo. Never add a separate latest/daily report section above the hero or wrap the homepage in another report list.
- Do not recreate `app/page-legacy.tsx` or split the homepage into a legacy page plus a new report wrapper.
- Before publishing, run `npm run lint`, `GITHUB_ACTIONS=true npm run build:pages` (use PowerShell environment syntax on Windows), and `node --test tests/homepage-layout.test.mjs tests/site-design.test.mjs tests/market-calendar.test.mjs`.
- The tests verify both legacy routes and content-driven daily reports. Do not weaken or delete these checks to make a publication pass.
- Check that the public homepage starts with the photo below the header, the new report appears in the existing latest/archive sections, and the individual report URL works.
- For daily automation, prefer one completed JSON write to `main` after reading the latest main. Never publish a placeholder, empty body, incomplete sources, or a second same-day file.
- Read `CLOUD_AUTOMATION.md` for the publication completion contract. Saving a file on an article branch is only saved work; a PR build does not deploy. Complete the authorized main write/merge and verify the exact main SHA's successful Pages build/deploy before reporting publication.
- Run `node --test tests/publication-verification.test.mjs` with the existing checks. After deployment, run `npm run verify:publication -- YYYY-MM-DD FULL_MAIN_COMMIT_SHA`. A nonzero result, including a stale homepage or failed network read, means publication is not yet verified. Never weaken this gate or bypass an access denial.

## Editorial titles for new daily and weekly reports

- Approved title-policy baseline: 2026-10-07 JST. This policy governs repository authoring; the separately configured generation job must be checked independently before claiming its configuration changed.
- Write one concise, unique, content-specific `title` from the article's actual subject. Lead with the important company, market development or reader question. Keep the daily/weekly report type in `kind` / the small `label`, rather than making a generic report name plus date the main title.
- A date or covered week may follow the subject when useful. Do not impose an arbitrary 32-character limit, stuff keywords, promise search ranking, or invent causality or certainty that the body and sources do not support.
- Daily JSON `title` is authoritative for the article H1, homepage/archive cards, HTML title, Open Graph and Twitter title. Use `createArticleMetadata` for search/sharing metadata. The `Market Note` suffix is allowed. `headline` is a legacy fallback; retain it as an identical alias of `title` in new JSON for compatibility with external tooling. The renderer also tolerates older inputs missing one title field, and must never blank a valid title.
- Use a short factual `description` summarizing that same subject; search, Open Graph and Twitter descriptions share it. Preserve URLs/slugs, publication timestamps and data baseline dates when changing a title. Do not silently retitle older archives in bulk.
- For static weekly routes, place the authoritative title and description in `content/editorial-titles.json`, reference that entry in the route H1 and `createArticleMetadata`, and let `withEditorialTitle` supply its homepage/archive title. Untouched legacy entries keep their existing title.
- Verify rendered H1, card title, HTML title, `og:title`, `twitter:title` and descriptions agree, allowing only the brand suffix. Run `node --test tests/article-titles.test.mjs` alongside the existing checks. Keep the article body, sources, URL and publication-date preservation checks.
- The strict read-only publication verifier supports both legacy and redesigned semantic containers. Keep `tests/redesign-publication.test.mjs`: its positive test uses the actual export and its negative tests reject missing, altered, reordered or hidden content, sources and metadata. Local export validation is not a deployed-site check.
